# 09 · Docker Manager

A tiny Flask service that owns the Docker socket so **Barista itself
doesn't have to**. This is Barista's single privileged boundary.

```
┌───────── barista-net (internal Docker network) ──────────┐
│                                                          │
│   ┌─ container: barista-bench-default ──┐                │
│   │  (Frappe + Barista app)             │   HTTP / token │
│   │  NO /var/run/docker.sock!  ─────────┼──────────────┐ │
│   └──────────────────────────────────────┘             │ │
│                                                         ▼ │
│                                  ┌─ container: barista-docker-manager ─┐
│                                  │  Flask + Docker SDK                  │
│                                  │  binds 10.x.x.x:8080 on barista-net │
│                                  │  /var/run/docker.sock (rw)           │
│                                  │  $HOME/.barista/data (rw, for bind- │
│                                  │  mount path resolution)              │
│                                  └─────────────────┬────────────────────┘
│                                                    │                   │
│                                                    ▼                   │
└──────────────────────────────────── /var/run/docker.sock ──────────────┘
                                                     │
                                            ┌────────▼────────┐
                                            │  Docker daemon  │
                                            └─────────────────┘
```

## Why a separate service

1. **Smaller attack surface.** The agent code that called the Docker
   SDK from inside Barista was ~500 lines of Python sharing a process
   with Frappe — anything in the bench's import path (user-installed
   apps!) could in principle reach the socket. Splitting it out means
   the Barista container can run *without* the socket at all.
2. **Independent audit.** docker-manager is ~600 lines, no Frappe, no
   user code, no eval-shaped APIs. Reviewable in an afternoon.
3. **Restart independence.** A `bench restart` in the control plane
   doesn't drop in-flight builds.
4. **Single chokepoint for policy.** Container limits, image
   allowlists, label prefixes, etc. are enforced in one place.

## Access boundary

Three layers, all required:

1. **Network**: docker-manager is on `barista-net` only. No
   `-p` mapping. It's not reachable from the host or the internet.
2. **Token**: every request must carry
   `X-Auth-Token: <BARISTA_DOCKER_MANAGER_TOKEN>`. The token is a
   32-byte hex string generated by `install.sh`, injected into both
   docker-manager and the Barista control-plane container via env.
3. **IP allowlist**: at boot, docker-manager reads its own
   `barista-net` subnet (`docker network inspect`) and refuses
   requests from sources outside that CIDR. This is a defense in
   depth against a future maintainer accidentally adding `-p` to the
   compose file.

Optional 4th layer for paranoid setups: docker-manager can *also*
listen on a Unix domain socket at `/run/docker-manager.sock`, which
is bind-mounted into the Barista container instead of using the
network. `install.sh --socket-only` enables this; the network
listener turns off.

## API

Versioned at `/v1/`. All bodies are JSON; all errors are
`{"error": "<kind>", "message": "..."}` with appropriate HTTP codes.

### Health

```
GET  /v1/health           → 200 {"ok": true, "docker_version": "..."}
GET  /v1/info             → docker daemon info + manager version
```

### Images / builds

```
POST /v1/builds
   body: { "tag": "barista/bench-erpnext-v15:abc1234",
           "dockerfile": "<contents>",
           "build_args": { ... },
           "context_files": { "entrypoint.sh": "<contents>", ... } }
   → 202 { "build_id": "b-<uuid>" }

GET  /v1/builds/<id>      → status + last log lines
GET  /v1/builds/<id>/log?since=<byte_offset>
                          → text/event-stream of log chunks
DELETE /v1/builds/<id>    → cancel

POST /v1/images/pull
   body: { "ref": "ghcr.io/frappe/bench-base:python3.11-node20" }
   → 202 { "pull_id": "p-<uuid>" }   (same polling shape as builds)
```

Notes on build context: instead of having Barista upload a tarball,
the caller sends a `dockerfile` string plus a flat dict of small
files (`entrypoint.sh`, etc.). docker-manager stages them in a temp
dir, runs `docker build` via SDK, streams the log into an in-memory
ring buffer, and tears down. This keeps the API surface narrow — no
file uploads, no tarballs, no path traversal traps.

### Benches (containers)

```
POST /v1/benches
   body: {
     "name": "myproject",                       # → container "barista-bench-myproject"
     "image": "barista/bench-myproject:abc1234",
     "host_path": "/home/user/.barista/data/benches/myproject",
     "http_port": 18001,
     "cpu_quota": 4,
     "mem_limit_mb": 4096,
     "labels": { "barista.spec": "erpnext-v15" },
     "traefik": { "host": "myshop.example.com", "tls": true }
   }
   → 201 { "container_id": "d3f8e1c9..." }

GET    /v1/benches                  → list of managed containers (label=barista.role=bench)
GET    /v1/benches/<name>           → inspect (status, IP, ports, limits)
POST   /v1/benches/<name>/start
POST   /v1/benches/<name>/stop
POST   /v1/benches/<name>/restart
POST   /v1/benches/<name>/update     # change cpu/mem limits in place
DELETE /v1/benches/<name>            # stop + remove; refuses unless ?force=true
GET    /v1/benches/<name>/logs?tail=200&since=<ts>
GET    /v1/benches/<name>/stats      → one-shot snapshot
WS     /v1/benches/<name>/stats/stream → 5s heartbeat of stats
```

### Exec

```
POST /v1/benches/<name>/exec
   body: { "cmd": ["bench", "--site", "myshop", "migrate"],
           "user": "frappe",
           "timeout_s": 600 }
   → 202 { "exec_id": "e-<uuid>" }

GET  /v1/benches/<name>/exec/<id>          → status + output (text)
GET  /v1/benches/<name>/exec/<id>/log?since=<offset>
                                            → tail
WS   /v1/benches/<name>/terminal?token=<one-shot>
                                            → interactive TTY (xterm.js)
```

The websocket terminal token is single-use and 60-second expiry,
minted by Barista via `barista.api.bench.exec_token` (which calls the
manager's `POST /v1/terminal-tokens`) so the Vue app never sees the
manager token directly.

### Networks

```
POST /v1/networks/ensure
   body: { "name": "barista-net" }
   → 200 { "id": "...", "subnet": "172.20.0.0/16" }
```

Idempotent; called by `install.sh` and by Barista on first boot.

### Proxy routing (Traefik dynamic config)

Barista never edits Traefik's config file. It pushes routes through
docker-manager, which owns the file:

```
PUT /v1/routes
   body: {
     "routes": [
       { "host": "myshop.example.com", "service": "barista-bench-myproject",
         "port": 80, "tls": true },
       ...
     ]
   }
   → 200 { "applied": 7 }
```

docker-manager renders these to
`/etc/traefik/dynamic.yml` (its bind mount), Traefik picks them up
via filesystem watch. No restarts.

## Long-running ops: build/pull/exec

Each long op has a row in an in-memory `tasks` dict (uuid → {status,
started_at, finished_at, log_buffer, future}). Buffer is a capped
deque (5 MB / 10 000 lines). Tasks survive for `Barista
Settings.long_task_ttl_min` (default 30 min) after completion, then
GC. If the manager restarts, all in-flight tasks are marked
`Cancelled` on next caller poll — Barista is expected to retry. This
is fine because every long op is idempotent (tag-based image build,
named container create, `bench migrate` is a no-op on re-run).

Implementation: a small `ThreadPoolExecutor(max_workers=N)` runs
tasks; `N` defaults to `Barista Settings.max_concurrent_builds * 2`.
No Celery, no Redis — this service is one process.

## Container constraints enforced by the manager

Even if a caller asks for something risky, the manager refuses:

| Caller asks                   | Manager does |
|--------------------------------|--------------|
| `privileged: true`             | reject       |
| `cap_add: [SYS_ADMIN, ...]`    | only the bench-needed caps are allowed; rest rejected |
| bind-mount `/`                 | reject any host path outside `$BARISTA_HOME/data` and `$BARISTA_HOME/backups` |
| `network: host`                | reject; only `barista-net` allowed |
| port-publish on `0.0.0.0`      | rewrite to `127.0.0.1` |
| image not in allowed registries| reject; allow-list is `ghcr.io/frappe/*`, `mariadb`, `redis`, `traefik`, `barista/*` |

This is the "policy chokepoint" the split is really for. Barista
*could* try to do something dumb (or be tricked into doing so by a
bug); docker-manager is the line of defense.

## File layout

```
barista/docker-manager/
├── Dockerfile
├── requirements.txt
├── README.md
└── src/
    ├── app.py              # Flask app + WSGI entrypoint
    ├── auth.py             # token + IP allowlist middleware
    ├── manager.py          # Docker SDK wrapper
    ├── builds.py           # build/pull task runner
    ├── exec.py             # one-shot exec + websocket terminal
    ├── routes.py           # Traefik dynamic.yml renderer
    ├── policy.py           # validation: image allowlist, mount allowlist, caps
    └── tasks.py            # in-memory task table + threadpool
```

The image is `python:3.12-slim` + `pip install docker flask
gevent-websocket` + the `src/` directory. ~80 MB.

## Concurrency / locking

One global `RLock` per bench name (held in a dict). Lifecycle ops on
the same bench are serialised; ops on different benches are
parallel. Builds don't take this lock; they're tagged by `tag` and
duplicate concurrent builds for the same tag are coalesced into one
task (later caller gets the existing `build_id`).

## Observability of docker-manager itself

- `GET /v1/metrics` returns Prometheus-format counters (requests by
  route, build durations, container ops by kind, errors).
- Logs go to stdout in JSON: `{ts, level, op, target, latency_ms,
  status}`. Barista doesn't read these directly; `docker logs
  barista-docker-manager` is the source of truth.

## Failure modes & how Barista reacts

| docker-manager state | Barista UI behaviour |
|----------------------|----------------------|
| Healthy              | normal |
| Slow (p95 > 2s)      | toast "Docker is slow"; per-bench status falls back to "Unknown" rather than blocking the UI |
| Down                 | red banner across the app: "Docker manager unreachable. Containers continue to run; you can't start, stop, or build until it returns." Reads of cached state still work. |
| Returns 5xx on op    | the corresponding `Bench Action` is marked `Failure` with the error; user can retry |

The `barista-agent` queue worker pings `GET /v1/health` every 10s and
publishes the status to `realtime: docker-manager:status` so the UI
can render the banner.

## Why Flask?

It's a 600-line service. Anything heavier (FastAPI, etc.) buys
nothing here. The `gevent-websocket` worker handles the terminal
streams; the rest is plain blocking HTTP. No async/await in this
codebase — keeps it boring.
