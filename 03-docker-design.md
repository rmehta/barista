# 03 · Docker Design

## Image hierarchy

```
ghcr.io/frappe/bench-base:python<X>-node<Y>
        │
        ▼
barista/bench-<spec>:<short_sha>   ← built per Bench Spec
        │
        ▼  (run-time)
container barista-bench-<name>     ← one Bench Host
```

### Base image (`bench-base`)

Owned by the Frappe org and reused here (already published for
`frappe-docker`). Contains:

- Debian slim
- Python (pyenv'd to the chosen version)
- Node (nvm'd to the chosen version)
- `wkhtmltopdf` 0.12.6 patched-qt
- `bench` CLI
- a non-root `frappe` user (uid 1000)
- `supervisord`, `nginx`

We do **not** rebuild this — we pin tags.

### Per-spec image

Built by Barista when a `Bench Spec` is saved (or rebuild is triggered).
The Dockerfile is templated and stored on the corresponding `Bench
Build` row for traceability. Sketch:

```dockerfile
ARG BASE
FROM ${BASE}

USER frappe
WORKDIR /home/frappe

RUN bench init --skip-redis-config-generation --frappe-branch={{ frappe_branch }} bench

WORKDIR /home/frappe/bench

{% for app in apps %}
RUN bench get-app --branch {{ app.branch }} {{ app.repository_url }}
{% endfor %}

# entrypoint is not the supervisord — supervisord is configured at
# runtime via a bind-mounted config so we can toggle workers without
# rebuilding.
COPY --chown=frappe:frappe entrypoint.sh /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
```

Build is invoked via the **low-level Docker Python SDK** (`docker.from_env().images.build`),
streamed line-by-line into `Bench Build.build_log` and broadcast via
realtime so the UI can show it live.

Image tag: `barista/bench-<spec>:<git_sha_of_lockfile>`. The "lockfile"
is the deterministic JSON dump of `{spec, apps[].source, apps[].branch,
apps[].commit}` so the same inputs always tag the same image.

## Run-time container layout

```
container barista-bench-<name>
│
├── /home/frappe/bench   (←  bind-mounted from host:
│   ├── apps/             ~/.barista/data/benches/<name>/  )
│   ├── sites/
│   ├── logs/
│   └── config/
│
├── supervisord runs:
│     - nginx               :80 inside, mapped to <http_port> on host
│     - gunicorn (frappe)   :8000 inside
│     - frappe-schedule
│     - frappe-worker-default
│     - frappe-worker-long
│     - frappe-socketio     :9000 inside
│
└── no Redis, no MariaDB    ← those are shared sidecars
```

## Shared infrastructure containers

Created once by `install.sh` and `docker compose up -d`.

### `barista-mariadb`

- Image: `mariadb:11`
- Port: `127.0.0.1:13306:3306` (only on loopback by default)
- Volume: `~/.barista/data/mariadb`
- Config: `~/.barista/config/mariadb/my.cnf`
- One server, many DBs (one per site). Created on demand by the agent
  worker via `CREATE DATABASE` + `GRANT`.
- Slow log enabled (path: `/var/log/mysql/slow.log`, also bind-mounted),
  threshold from `Barista Settings`.
- Binary log enabled when `Barista Settings.binlog_enabled` is true.
  Toggling regenerates `my.cnf` and restarts the container.

### `barista-redis`

- Image: `redis:7-alpine`
- Two logical Redis databases per site (cache, queue) handed out by
  Barista at site creation. We don't run separate Redis processes per
  bench — we shard by `bench-name-cache` / `bench-name-queue` and write
  the right URLs into each site's `common_site_config.json`.

### `barista-net` network

User-defined bridge network so containers can resolve each other by
name. Site config uses `barista-mariadb:3306` and `barista-redis:6379`
as host references — never `localhost`.

## Networking & TLS

- **Inside Docker**: every container on `barista-net`. Bench containers
  expose nothing publicly, only to the host.
- **From host**: every bench's nginx is published on
  `127.0.0.1:<http_port>`, where `<http_port>` is auto-allocated from
  `Barista Settings.http_port_range_start` (default 18000).
- **From the internet** (self-hosted server case): a single top-level
  **`barista-traefik`** container (also created by `install.sh`) terminates
  TLS on :80/:443 and routes by Host header to the right bench's
  internal port. Routing rules are generated by Barista whenever a
  `Site` row changes — written to
  `~/.barista/config/traefik/dynamic.yml` (Traefik watches it).
- Let's Encrypt is wired via Traefik's built-in ACME for sites whose
  `Site Domain.tls` is checked.

Reasonable people may prefer Caddy; switching is one template file. The
spec uses Traefik because its file-based dynamic config is friendlier
to "Frappe writes a YAML file" workflows than Caddy's API mode.

## Volumes & ownership

| Path on host                                | Mounted into                          | Mode |
|---------------------------------------------|---------------------------------------|------|
| `~/.barista/data/benches/<name>/`           | `/home/frappe/bench` in that bench    | rw   |
| `~/.barista/data/mariadb/`                  | `/var/lib/mysql` in `barista-mariadb` | rw   |
| `~/.barista/data/redis/`                    | `/data` in `barista-redis`            | rw   |
| `~/.barista/backups/`                       | `/backups` in control-plane bench     | rw   |
| `~/.barista/config/mariadb/my.cnf`          | `/etc/mysql/conf.d/my.cnf`            | ro   |
| `~/.barista/config/traefik/`                | `/etc/traefik/`                       | ro   |
| `/var/run/docker.sock`                      | same path, in control-plane bench     | rw   |

All bench-bound paths are owned by uid 1000 (the `frappe` user inside
the container). `install.sh` sets that up explicitly with `chown`.

## Lifecycle operations

Each maps to a single method on `barista.tasks.bench` and a `Bench Action`.

| Op       | What happens |
|----------|--------------|
| Create   | Pull base image (if missing) → build per-spec image → `docker create` with bind mounts, port, limits → `docker start` → wait for nginx :80 to answer → write Site row for control-plane on first install, otherwise mark Running. |
| Start    | `docker start`. Wait for healthcheck. |
| Stop     | `docker stop` (10s grace). |
| Restart  | `docker restart` if running, else Start. |
| Rebuild  | New `Bench Build`. On success, swap `current_build`, recreate container with new image, restart sites' workers. Old image is kept; user can roll back from the UI. |
| Destroy  | Refuse if non-archived sites exist. Stop, remove container, leave `host_path` intact (data is precious — user must `rm -rf` manually). |
| Exec     | The "Open Terminal" feature pipes a `docker exec -it bench bash` through a websocket. |

## Healthchecks

Every bench container has an HTTP healthcheck:

```
HEALTHCHECK --interval=15s --timeout=5s --start-period=30s --retries=3 \
  CMD curl -fsS http://localhost/api/method/ping || exit 1
```

The agent worker polls `docker.containers.list()` every 15 seconds and
syncs each `Bench Host.status` accordingly, publishing realtime updates
on change. Polling is fine at single-host scale (≪ 100 containers); we
don't subscribe to Docker events to keep the code path boring.

## Resource limits

`cpu_quota` (in cores) and `mem_limit_mb` on `Bench Host` map to
`--cpus` and `--memory`. Zero means unlimited (the default; opt-in
limiting via the UI). Limits are applied via `container.update()` so
they can be changed without restart.

## Why one MariaDB and one Redis for everything?

- It's how `frappe-bench` works locally already; the mental model is
  familiar.
- DB-level isolation per site is enough for a single-host dev tool.
  Real isolation would mean a MariaDB-per-bench, which costs ~150 MB
  of RAM each — punitive on a laptop.
- The user can opt out by creating sites with an external
  `db_host` (form field on `Site`, advanced section). Then Barista
  doesn't touch MariaDB for that site at all.
